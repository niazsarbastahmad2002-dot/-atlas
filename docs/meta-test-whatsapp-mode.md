# Atlas Meta WhatsApp test mode

Atlas can exercise its WhatsApp transport against Meta's official Cloud API test phone number without touching the real +964 sender or clinic Coexistence records.

## Safety boundary

- `ATLAS_WHATSAPP_MODE=meta_test` selects only `WHATSAPP_TEST_*` credentials.
- Test mode is rejected when `VERCEL_ENV=production`.
- Every test recipient must be present in `WHATSAPP_TEST_ALLOWED_RECIPIENTS` as E.164.
- The existing production `WHATSAPP_*` credentials and clinic-scoped Coexistence rows are never overwritten by this mode.
- `/api/whatsapp/test/bootstrap` and `/api/whatsapp/test/send` are non-production-only and require `WHATSAPP_TEST_ADMIN_SECRET`.
- The normal production reminder cron is intentionally not repointed at the test sender. Development sends use the protected test dispatcher instead, so testing cannot claim live reminder jobs.

## Test assets

Configure these only in a non-production environment:

```env
ATLAS_WHATSAPP_MODE=meta_test
WHATSAPP_TEST_ENABLED=true
WHATSAPP_TEST_ACCESS_TOKEN=<Meta temporary/system test token>
WHATSAPP_TEST_PHONE_NUMBER_ID=<Meta test phone-number ID>
WHATSAPP_TEST_WABA_ID=<Meta test WABA ID>
WHATSAPP_TEST_APP_SECRET=<Meta app secret>
WHATSAPP_TEST_VERIFY_TOKEN=<random test webhook verify token>
WHATSAPP_TEST_GRAPH_API_VERSION=v26.0
WHATSAPP_TEST_GLOBAL_DAILY_LIMIT=100
WHATSAPP_TEST_ALLOWED_RECIPIENTS=+9647XXXXXXXXX
WHATSAPP_TEST_ADMIN_SECRET=<random 24+ character secret>
```

Do not copy the real +964 sender token or phone-number ID into the test variables.

## Template bootstrap

The protected test bootstrap creates or reuses:

- `atlas_visit_confirm_v1` — appointment confirmation reminder.
- `atlas_visit_today_v1` — day-of appointment reminder.
- `atlas_login_otp_v1` — Meta AUTHENTICATION template with an OTP copy-code button.
- `atlas_staff_invite_v1` — secure receptionist invitation link.

Meta may still place newly created templates into review. The endpoint reports the provider status; it does not bypass Meta review.

## Login and signup OTP

Supabase remains the authentication authority. Atlas never creates or verifies its own OTP.

For direct Meta delivery, Supabase's Send SMS Hook calls `/api/auth/send-sms-hook`. The signed hook contains the six-digit OTP generated by Supabase. Atlas verifies the Standard Webhooks signature, enforces the Meta test recipient allowlist, and sends that OTP through `atlas_login_otp_v1`. The user then submits the code to the existing Supabase `verifyOtp(..., type: "sms")` flow.

This is different from Supabase's native `channel: "whatsapp"`, which currently requires Twilio/Twilio Verify. When direct Meta mode is active, Atlas deliberately does not request that native channel.

Because a Supabase Send SMS Hook replaces the project's SMS transport, direct-Meta mode is presented as WhatsApp-only in Atlas. Do not label the same hooked delivery as SMS.

Non-production activation flags:

```env
NEXT_PUBLIC_ATLAS_DIRECT_META_OTP_ENABLED=true
WHATSAPP_DIRECT_OTP_ENABLED=true
```

Phone Auth itself must also be enabled in the Supabase environment used for the test, and the Send SMS Hook must be configured with its generated signing secret. Do not change the live Atlas Supabase Auth configuration merely to exercise this branch.

## Receptionist invitations

Set in the non-production environment:

```env
NEXT_PUBLIC_ATLAS_WHATSAPP_DIRECT_INVITES_ENABLED=true
WHATSAPP_DIRECT_INVITES_ENABLED=true
```

The existing one-use invitation is still created server-side, expires after 24 hours, and is redeemed through the existing `/join/<token>` flow. WhatsApp is only the delivery transport. In test mode the recipient must be on the test allowlist.

## Appointment reminders

Use the protected `/api/whatsapp/test/send` dispatcher with `kind: "reminder"`. It calls the same Meta Cloud API payload builder used by Atlas reminders, but it does not consume or mutate the production reminder queue.

This separation is intentional. Production continues to resolve each clinic's real Meta sender from its existing Coexistence connection. Once Meta production approval is complete, Atlas keeps the same message builders and switches back to `ATLAS_WHATSAPP_MODE=production` plus the approved production credentials/connections.

## Promotion rule

Never merge test credentials into Git, never add them to production environment variables, and never set `ATLAS_WHATSAPP_MODE=meta_test` in production. Before enabling production OTP or direct staff delivery, require approved production templates, a real authorized sender, end-to-end delivery, successful Supabase OTP verification, rate-limit tests, and the normal Atlas release gate.
